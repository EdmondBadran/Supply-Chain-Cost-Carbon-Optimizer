What happens to the file you upload

Your file is used to create your analysis and nothing else. The results live only in the memory of the process that answered your request, only for your session, and are gone when you clear them, after {{ store_stats.idle_timeout_minutes // 60 }} hours without activity, or whenever that process stops.

Where this runs

Overlap is hosted on Vercel as a serverless function. Vercel is the processor that runs the code and carries the traffic, so your request, including the file on it, passes through their infrastructure, and their own terms and privacy notice apply to that. There is no other third party in the path: no analytics, no tracking pixels, no outbound API calls with your data in them, and no accounts.

The function runs in a single region. Which one is a deployment setting rather than a promise on this page, so if the location of processing matters to you, ask before uploading.

Is my file stored?

No. The upload is written to a temporary file only long enough to read it, because a CSV reader needs something to read, and that file is deleted before the request finishes, whether the analysis worked or not. What remains is the analysis, in an in-memory database that is never written to disk. There is no database behind this tool, no object storage and no backups, so there is nothing holding your file after the request that carried it.

Your file may contain personal data

That is worth saying plainly, because order exports often do. A customer name in a destination field, a delivery address, a contact, an identifier that ties a shipment to a person: any of these can ride along in a column the analysis does not even use. Overlap does not ask for them and does not need them.

Strip what you can before uploading. The five columns the tool requires are a place, a place, a weight, a mode and an origin name. If the rest of the file can go, let it go. Whatever does arrive is treated the same as the rest of the file: held in memory for your session, never written to disk, never logged, and dropped with the workspace.

Cookies

One cookie, and it is necessary rather than optional, which is why there is no banner asking you to accept it. It is signed so it cannot be forged, it carries two random values and nothing else, and it expires when you close your browser.

  • Which workspace in memory is yours.
  • A token proving a form you submit came from a page this site served you.

There is no advertising cookie, no analytics cookie and no third party cookie. Nothing in it identifies you, and it is useless to anybody who copies it once the workspace behind it is gone.

What gets logged

State changes are written to the application log as one JSON line each: that an upload was loaded, how many rows it had, how many were skipped, how many routes came out, that a sample was loaded, that a workspace was cleared, that somebody hit a rate limit. Deliberately counts rather than content: no city, no customer, no company name, no filename, no column from your file.

Vercel keeps its own request logs, which carry the usual things a web server records, including IP address, and are retained under their policy rather than this one. The audit log above is the only thing Overlap itself writes, and it goes to the same place.

When is it deleted?

After {{ store_stats.idle_timeout_minutes }} minutes without a request, your workspace is dropped. Pressing Clear this data on the upload page drops it immediately, which is the fastest deletion this tool offers and needs no request to anybody. A serverless instance that restarts or is replaced drops every workspace it was holding, including yours, possibly sooner than either of those.

There is no retention period to quote beyond that, because there is nowhere for anything to be retained. Equally, there is no way to ask for a copy of your data later, or to restore an analysis you lost: it does not exist once the workspace is gone.

What this does not claim

The server can read your data while it is analysing it. It has to: it is the thing doing the analysis. Anyone with access to the running process could in principle read what is in its memory. Making that untrue would mean encrypting the file in your browser and doing the whole calculation there, which is a different and much larger piece of software.

This is not a GDPR compliance statement. No data protection assessment has been done, there is no data processing agreement on offer, and nothing here has been certified. What is written above is an accurate description of the code, which is a different and smaller claim.

So the honest version is the one above: nothing is stored, nothing is shared between visitors, nothing is sent anywhere by this tool, and the window in which your analysis exists at all is your session, on one instance, which may end before you do.

Limits worth knowing

  • Uploads are capped at {{ max_mb }} MB and must be CSV.
  • The instance answering you holds at most {{ store_stats.limit }} sessions at once. Past that the least recently used one is dropped, which costs that visitor their upload and nothing else.
  • Right now this instance is holding {{ store_stats.live }} workspace{{ "s" if store_stats.live != 1 }} in memory. Another instance would give a different number, because they share nothing.
  • Nothing survives a restart, and a serverless deployment restarts and moves between instances on its own schedule. Export anything you want to keep.

All of this is in optimizer/store.py, optimizer/security.py and the upload handler in app.py, which are worth reading rather than believing.
